1. Core Philosophy

TEREN Hotels is built on principles that prioritize user experience, technical integrity, and outdoor-first design.

Guest-First

Every technical decision serves the end user—hotel staff who need fast, reliable tools under real-world conditions (sunlight, motion, time pressure).

Elegance Over Complexity

Clean architecture, minimal boilerplate, no framework magic. We choose clarity and maintainability over clever abstractions.

Outdoor-First Design

High contrast, legible typography, warm stone backgrounds that reduce glare. Built for receptionists using tablets in bright hotel lobbies.

Respect for Time

Optimized for speed: < 1.5s page loads on 4G, optimistic UI updates, zero unnecessary loading screens.

3. Key Technical Decisions

Clean Architecture Light

Separation of concerns without over-engineering:

  • Handlers → HTTP logic only
  • Services → Business rules
  • Repositories → Database queries
  • Models → Domain entities

Why: Testable, maintainable, developers can understand years later.

Raw SQL over ORM

We use pgx with raw SQL queries instead of GORM or similar:

  • Full control over query performance
  • No "magic" hidden queries
  • Complex availability queries (overlap detection)
  • Explicit is better than implicit

Why: Technical integrity, predictable performance.

Grid-Based Room Layout

12 columns × 20 rows grid system (not pixels):

  • pos_x: 0-11
  • pos_y: 0-19
  • Constraint: UNIQUE(floor_id, pos_x, pos_y)

Why: Spec FMB-001 §4.1, enables drag-and-drop layout builder, prevents overlapping rooms.

Multi-Tenant via property_id

Every table has property_id UUID:

  • Room numbers unique per property (not per floor)
  • Future-ready for Row-Level Security (RLS)
  • Isolation between hotels

Why: BR-08 compliance, SaaS scalability.

Optimistic UI Updates

Frontend updates immediately, then syncs with backend:

  • Room token changes color instantly
  • If API fails → rollback + toast notification
  • User never waits for spinner

Why: Respect for Time, feels instantaneous.

No Modal Forms

Progressive Disclosure via inline expansion:

  • Block room form expands in drawer
  • Assign booking shows inline list
  • Never blocks the user's flow

Why: Context preservation, aligned with TEREN Design System §3.5.

⚠️ Critical Constraints

Never commit .env files — Use .env.example as template. Production secrets live in Railway Variables UI only.
Always use transactions for batch operations (AC-13: all-or-nothing layout saves).
Validate grid bounds (BR-06: pos_x 0-11, pos_y 0-19) before any database operation.

4. Development Workflow

4.1 Environment Separation

Aspect Development (Local) Production (Railway)
Database postgres://teren_dev:teren_dev@localhost:5432/teren_hotels Railway auto-injected DATABASE_URL
Environment File .env.development.local (not committed) Railway Variables UI
Hot Reload Air (Go) + Vite (Svelte) N/A (production build)
Log Level debug info or warn
CORS localhost:5173, localhost:3000 hotels.teren.dev

4.2 Daily Development Flow

  1. Start Local Stack

    docker-compose up -d → Starts PostgreSQL, backend (with hot reload), and frontend.

    Verify: docker-compose ps shows all services as "Up".

  2. Run Migrations

    go run cmd/migrations/main.go o ./run-migrations

    Creates tables, applies schema corrections, seeds test data.

  3. Develop & Test

    Edit code → Auto-reload in browser. Backend logs appear in docker-compose logs -f backend.

    Run tests: docker-compose exec backend go test ./... -v

  4. Commit & Push

    git add . && git commit -m "feat: description" && git push origin feature/branch

    Create Pull Request on GitHub for review.

  5. Merge to Main

    After PR approval, merge to main branch.

    Railway detects push → auto-deploys to production.

✅ Best Practices

Always test migrations locally before pushing.
Write reversible migrations (both .up.sql and .down.sql).
Use feature branches (never commit directly to main).
Run go vet and go fmt before committing.

5. Deployment to Railway

5.1 Pre-Deploy Checklist

  • ✅ All tests passing locally
  • ✅ Migrations tested and reversible
  • ✅ .env files NOT committed
  • ✅ Dockerfile builds successfully: docker build -t teren-backend .
  • ✅ CORS origins updated for production domain

5.2 Railway Setup (One-Time)

  1. Create Project: Railway.app → New Project → Deploy from GitHub repo
  2. Add PostgreSQL: New → Database → PostgreSQL (auto-creates DATABASE_URL)
  3. Configure Variables: 
    APP_ENV=production
SERVER_PORT=8080
JWT_SECRET=$(openssl rand -hex 32)
JWT_EXPIRY=24h
CORS_ALLOWED_ORIGINS=https://hotels.teren.dev
LOG_LEVEL=info
  4. Set Root Directory: Service Settings → Root Directory = backend

5.3 Deploy Commands

# Option 1: Auto-deploy (recommended)
git push origin main
# Railway detects push → builds → deploys automatically

# Option 2: Manual deploy via CLI
railway link
railway up --detach

# Option 3: Force redeploy
railway restart

5.4 Post-Deploy Verification

  1. Health Check: curl https://your-app.up.railway.app/health → {"status":"ok"}
  2. Run Migrations: Railway shell → ./run-migrations
  3. Check Logs: railway logs or Railway Dashboard → Deployments → View Logs
  4. Test Frontend: Open production URL, verify no CORS errors in DevTools
🚨 Common Issues

"go.sum not found" → Ensure Dockerfile is in backend/ folder and Railway Root Directory is set correctly.
"DATABASE_URL not found" → Railway auto-injects this when PostgreSQL service is linked. Check Variables tab.
CORS errors → Update CORS_ALLOWED_ORIGINS with exact frontend URL (no trailing slash).
